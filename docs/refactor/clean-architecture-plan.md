# 厚東川監視システム - クリーンアーキテクチャリファクタリング計画

## 概要
現在の2,700行のモノリシックなstreamlit_app.pyを、クリーンアーキテクチャの原則に基づいて再設計・実装する。

## 現状分析

### 問題点
1. **巨大な単一ファイル**: streamlit_app.py（2,727行）に全ロジックが集中
2. **責務の混在**: UI、データ取得、ビジネスロジック、状態管理が混在
3. **テスト困難**: UIとロジックの密結合によりユニットテスト不可能
4. **拡張困難**: 新機能追加時に既存コードへの影響範囲が予測困難
5. **設定の硬直性**: 設定値がコード内に散在

### 現在の主要機能
- 河川・ダム水位データの表示
- 複数APIからのデータ取得（山口県、気象庁、Yahoo天気）
- リアルタイムアラート
- 履歴データグラフ表示
- 自動更新機能

## 目標アーキテクチャ

### レイヤー構成
```
presentation/     # プレゼンテーション層
├── app.py       # Streamlitエントリーポイント（薄いラッパー）
├── pages/       # ページコンポーネント
└── components/  # 再利用可能なUIコンポーネント

application/     # アプリケーション層
├── services/    # ユースケース実装
└── dto/         # データ転送オブジェクト

domain/          # ドメイン層
├── entities/    # ビジネスエンティティ
├── repositories/# リポジトリインターフェース
└── value_objects/# 値オブジェクト

infrastructure/  # インフラストラクチャ層
├── api/         # 外部API通信
├── persistence/ # データ永続化
└── cache/       # キャッシュ実装

config/          # 設定
└── settings.py  # 環境設定
```

### 依存関係の方向
```
Presentation → Application → Domain ← Infrastructure
```

## 実装フェーズ

### Phase 1: 基盤整備（破壊的変更なし）
1. ディレクトリ構造の作成
2. ドメインモデルの定義
3. リポジトリインターフェースの定義
4. 既存コードからのロジック抽出

### Phase 2: インフラストラクチャ層の実装
1. API通信クラスの実装
2. データ永続化層の実装
3. キャッシュ機構の実装

### Phase 3: アプリケーション層の実装
1. サービスクラスの実装
2. DTOの定義
3. ユースケースの整理

### Phase 4: プレゼンテーション層の再構築
1. UIコンポーネントの分離
2. ページ構造の整理
3. 状態管理の改善

### Phase 5: 切り替えと検証
1. 新アーキテクチャへの段階的移行
2. 旧実装との並行稼働
3. 完全切り替え

## リスク管理

### 安全性確保
- 各フェーズでテストを実装
- 旧実装を保持し、いつでもロールバック可能
- 段階的な移行により影響範囲を限定

### 互換性維持
- 既存のデータフォーマットは変更しない
- UIの見た目は可能な限り維持
- 設定ファイルの後方互換性確保

## 成功基準
1. テストカバレッジ80%以上
2. 各モジュールが独立してテスト可能
3. 新機能追加時の影響範囲が明確
4. コードの可読性向上（1ファイル500行以下）
5. 依存関係が明確で循環依存なし
